# План перехода проекта Carsharing на микросервисы

## Цель

Перевести текущий .NET-монолит Carsharing на микросервисную архитектуру без резкого переписывания всей системы. Переход должен идти постепенно: сначала выделяются границы доменов и контракты, затем отдельные сервисы, базы данных, события и инфраструктура.

План основан на текущих сущностях проекта:

- `User`
- `Client`
- `ClientDocument`
- `Car`
- `Booking`
- `Trip`
- `Bill`
- `Payment`
- `Fine`
- `Maintenance`
- `Insurance`
- `Tariff`
- `Promocode`
- `Review`
- `Favorite`

Также в план добавлены компоненты, необходимые для реального каршеринга: телематика, микроконтроллеры в автомобилях, платежный шлюз, уведомления, dangerous driving, начисление штрафов и backoffice.

## Целевая архитектура

Основной принцип: у каждого сервиса своя зона ответственности, свои миграции и публичные контракты. К физически отдельным базам данных можно прийти постепенно: на раннем этапе допустима одна PostgreSQL-инстанция с отдельными схемами, если сервисы не читают и не меняют таблицы друг друга напрямую.

Рекомендуемый технический стек:

- API Gateway: YARP или Ocelot.
- Auth: JWT, refresh tokens, роли и permissions.
- Message Broker: RabbitMQ или Kafka.
- Data storage: PostgreSQL, сначала можно разделять сервисы схемами, затем отдельными базами.
- Cache: Redis, только если появится реальная потребность.
- Object Storage: MinIO или S3-compatible storage.
- Observability: сначала health checks, correlation id и structured logs; OpenTelemetry, Prometheus, Grafana, Loki или Seq можно добавить позже.
- Containerization: Docker Compose на первом этапе, Kubernetes на следующем.
- Communication: REST для синхронных запросов, события через broker для бизнес-процессов; gRPC можно добавить позже для внутренних высоконагруженных вызовов.

Паттерны, которые стоит вводить постепенно:

- Database per Service или schema per service как промежуточный шаг.
- Outbox Pattern для событий, влияющих на деньги, бронь и поездку.
- Inbox Pattern для критичных consumers.
- Idempotency keys.
- Saga только для процессов, где без нее появляются реальные распределенные транзакции.
- API versioning.
- Health checks.
- Correlation ID.
- Centralized logging.
- Contract tests для стабильных публичных контрактов, не для каждого чернового API.

## Геоданные и координаты

Проект продолжает использовать PostgreSQL/PostGIS и библиотеку координат в .NET, например NetTopologySuite. Координаты не стоит расписывать в моделях как отдельные `Latitude`/`Longitude`, если их нужно искать по радиусу, проверять попадание в геозону или строить маршрут.

Рекомендуемый подход:

- хранить точку как `geometry(Point, 4326)` или `geography(Point, 4326)`;
- хранить зоны как `geometry(Polygon, 4326)` или `geometry(MultiPolygon, 4326)`;
- в C# использовать `Point`, `Polygon`, `MultiPolygon` из NetTopologySuite;
- для простого отображения на клиенте отдавать DTO с `latitude` и `longitude`, но внутри БД и доменной модели держать геометрию;
- использовать GIST-индексы для поиска ближайших автомобилей и проверки геозон.

Такой вариант логичнее для каршеринга: Fleet Service владеет текущей позицией автомобиля и геозонами, Trip Service хранит точки маршрута поездки, Fine/Violation Service может хранить место нарушения.

## Как работают микросервисы

Этот раздел объясняет роль каждого сервиса не только через сущности, но и через реальные действия в системе. Главное правило остается общим: сервис владеет своей областью данных и не меняет таблицы другого сервиса напрямую. Для синхронных проверок используется API, для бизнес-процессов и слабой связности - события через брокер сообщений.

### Identity Service

Identity Service отвечает за пользователя как за учетную запись: регистрацию, вход, токены, роли и блокировку доступа. Он не хранит профиль клиента, документы, поездки, машины или платежи.

Типичный поток регистрации:

1. Мобильное приложение отправляет запрос на регистрацию через API Gateway.
2. Identity Service создает `User`, хеширует пароль или подтверждает телефон.
3. Сервис выдает JWT и refresh token.
4. Identity Service публикует `UserRegistered`.
5. Customer/Profile Service по этому событию может создать профиль клиента.

Типичный поток входа:

1. Пользователь отправляет телефон, пароль или код подтверждения.
2. Identity Service проверяет учетные данные.
3. Если пользователь не заблокирован, сервис выдает новый JWT.
4. Остальные сервисы принимают этот JWT и используют claims для проверки прав.

Identity Service должен быть максимально стабильным, потому что через него проходят все пользователи. Но на первом этапе не нужно делать сложную permission-систему: достаточно ролей клиента, администратора и оператора.

### Customer/Profile Service

Customer/Profile Service отвечает за бизнес-профиль клиента: ФИО, документы, статус допуска к аренде и избранные автомобили. Он связан с Identity Service через `UserId`, но не управляет паролями и токенами.

Типичный поток создания профиля:

1. Identity Service публикует `UserRegistered`.
2. Customer/Profile Service создает `Client` со статусом `Pending`.
3. Клиент заполняет личные данные.
4. Клиент загружает документы через Media/File Service.
5. Customer/Profile Service сохраняет `ClientDocument` со ссылкой на `FileId`.
6. Оператор подтверждает или отклоняет документы.
7. После успешной проверки сервис публикует `CustomerVerified`.

На первом этапе достаточно универсальной сущности `ClientDocument`. Отдельные модели паспорта и водительского удостоверения стоит добавлять только если появится сложная проверка документов.

### Fleet Service

Fleet Service владеет парком автомобилей: машинами, категориями, характеристиками, фото, статусами, доступностью, текущей позицией и геозонами. Если другой сервис хочет изменить доступность машины, он делает это через Fleet Service или через событие.

Типичный поток проверки автомобиля:

1. Мобильное приложение запрашивает список машин.
2. API Gateway отправляет запрос во Fleet Service.
3. Fleet Service возвращает только доступные автомобили, их характеристики, фото и координаты.
4. Координаты наружу можно отдавать как `latitude`/`longitude`, но внутри сервиса они хранятся через PostGIS/NetTopologySuite.

Типичный поток резервирования:

1. Booking/Trip Service проверяет доступность автомобиля.
2. Fleet Service атомарно переводит машину в `Reserved`.
3. Fleet Service публикует `CarReserved`.
4. Если бронь истекла или отменена, автомобиль возвращается в `Available`.

Fleet Service не должен рассчитывать оплату, проверять документы клиента или создавать штрафы. Его зона ответственности - состояние автомобиля и его доступность.

### Booking/Trip Service

Booking/Trip Service отвечает за основной жизненный цикл аренды: бронь, старт поездки, движение и завершение. В облегченном плане бронь и поездка находятся в одном сервисе, потому что они тесно связаны.

Типичный поток бронирования:

1. Клиент выбирает автомобиль и нажимает "Забронировать".
2. Booking/Trip Service проверяет, что у клиента нет активной брони.
3. Сервис проверяет доступность автомобиля через Fleet Service или локальную read model.
4. Создается `Booking` с временем истечения.
5. Автомобиль переводится в `Reserved`.
6. Публикуется `BookingCreated`.

Типичный поток старта поездки:

1. Клиент нажимает "Начать поездку".
2. Booking/Trip Service проверяет активную бронь и допуск клиента.
3. Создается `Trip`.
4. Фиксируется стартовое время, стартовая координата и состояние автомобиля.
5. Публикуется `TripStarted`.
6. Fleet Service переводит автомобиль в `InTrip`.
7. Telematics/IoT Service может отправить команду открыть автомобиль.

Типичный поток завершения поездки:

1. Клиент завершает поездку.
2. Booking/Trip Service фиксирует `EndTime`, `EndLocation`, длительность и дистанцию.
3. Публикуется `TripFinished`.
4. Billing/Payments Service создает счет.
5. Fleet Service возвращает автомобиль в доступность или отправляет его на обслуживание.

Booking/Trip Service не должен проводить оплату и не должен сам создавать штрафы. Он только фиксирует факт поездки и ее параметры.

### Pricing/Tariff Service

Pricing/Tariff Service отвечает за тарифы, промокоды и расчет стоимости. На первом этапе его можно не выносить физически, если тарифы простые. Но логически это отдельная зона, потому что правила расчета со временем быстро усложняются.

Типичный поток расчета:

1. Billing/Payments Service получает `TripFinished`.
2. Billing/Payments Service передает в Pricing/Tariff Service длительность, дистанцию, тариф и промокод.
3. Pricing/Tariff Service рассчитывает стоимость.
4. Billing/Payments Service создает счет на основе результата.

Для первого этапа достаточно явных полей тарифа: цена за минуту, километр, сутки и минимальная стоимость. Отдельные правила тарификации нужны позже, если появятся ночные тарифы, платное ожидание, зональные коэффициенты или сложные скидки.

### Billing/Payments Service

Billing/Payments Service отвечает за счета, начисления, задолженности и оплату. В облегченном плане счета и платежи можно держать вместе. Отдельный Payment Gateway Service нужен позже, когда появится реальная интеграция с платежным провайдером.

Типичный поток после завершения поездки:

1. Booking/Trip Service публикует `TripFinished`.
2. Billing/Payments Service получает событие.
3. Сервис создает `Bill`.
4. Сервис рассчитывает стоимость сам или через Pricing/Tariff Service.
5. Счет переходит в статус `PendingPayment`.
6. Клиент оплачивает счет.
7. Сервис создает `Payment`.
8. После успешного платежа публикуется `PaymentSucceeded`.
9. Счет переходит в статус `Paid`.

Важное правило: платежи должны быть идемпотентными. Если callback от платежной системы пришел дважды, второй вызов не должен создать вторую оплату или повторно закрыть счет с побочным эффектом.

### Payment Gateway Service

Payment Gateway Service стоит выделять отдельно, когда платежная логика становится сложнее: появляются webhooks, подписи провайдера, возвраты, несколько платежных методов и разные провайдеры.

Типичный поток с внешним провайдером:

1. Billing Service создает счет.
2. Payment Gateway Service создает платежную попытку.
3. Внешний провайдер возвращает ссылку на оплату или результат авторизации.
4. Клиент оплачивает.
5. Провайдер отправляет webhook.
6. Payment Gateway Service проверяет подпись webhook.
7. Сервис публикует `PaymentSucceeded` или `PaymentFailed`.
8. Billing Service обновляет счет.

Payment Gateway Service не должен сам менять бизнес-статус поездки. Его зона - надежная интеграция с платежной системой.

### Fine/Violation Service

Fine/Violation Service отвечает за нарушения, dangerous driving и штрафы. Он получает события от телематики, поездок или операторов и решает, нужно ли создать нарушение и штраф.

Типичный поток dangerous driving:

1. Telematics/IoT Service получает резкое торможение, ускорение, удар или превышение скорости.
2. Telematics/IoT Service публикует событие dangerous driving.
3. Fine/Violation Service создает `Violation`.
4. Сервис применяет правила штрафов.
5. Если штраф очевидный, создается `Fine`.
6. Если нужна проверка, штраф уходит в ручную модерацию.
7. После подтверждения публикуется `FineCreated`.
8. Billing/Payments Service добавляет начисление к счету.

Fine/Violation Service не должен сам списывать деньги. Он только создает факт нарушения и сумму штрафа.

### Telematics/IoT Service

Telematics/IoT Service отвечает за связь с бортовым устройством автомобиля: прием телеметрии, heartbeat, диагностику и команды к автомобилю. Для дипломного контура это сервис, который принимает данные от ESP32, GPS, GSM/GPRS и потенциально CAN-шины.

Типичный поток телеметрии:

1. Устройство отправляет координату, скорость, уровень топлива, пробег и состояние датчиков.
2. Telematics/IoT Service проверяет устройство и принимает пакет.
3. Сервис сохраняет `TelemetryPacket`.
4. Публикуется `TelemetryReceived`.
5. Fleet Service обновляет последнюю позицию автомобиля.
6. Booking/Trip Service может использовать данные для маршрута поездки.
7. Fine/Violation Service может реагировать на опасное вождение.

Типичный поток команды:

1. Клиент начинает поездку.
2. Booking/Trip Service публикует `TripStarted`.
3. Telematics/IoT Service отправляет команду открыть автомобиль.
4. Устройство возвращает результат команды.
5. Сервис сохраняет `VehicleCommandResult`.

Telematics/IoT Service не должен напрямую создавать штрафы, счета или поездки. Он источник технических данных и исполнитель команд.

### Notification Worker

Notification Worker отвечает за уведомления клиентам и операторам. На первом этапе это может быть worker без публичного API.

Типичный поток:

1. Сервис публикует событие, например `BookingCreated`, `BillIssued` или `PaymentSucceeded`.
2. Notification Worker получает событие из RabbitMQ.
3. Worker формирует сообщение.
4. Worker отправляет email, SMS, push или заглушку.
5. Worker сохраняет историю отправки.

Если Notification Worker временно не работает, основной бизнес-процесс не должен ломаться. Бронь, поездка и оплата должны завершаться независимо от отправки уведомления.

### Maintenance Service

Maintenance Service отвечает только за легкий учет обслуживания автомобиля в каршеринге. Это не CRM автосервиса и не система управления ремонтом.

Типичный поток:

1. После поездки, ДТП, жалобы или события dangerous driving автомобиль нужно проверить.
2. Fleet Service переводит автомобиль в `Maintenance` или `Unavailable`.
3. Maintenance Service создает запись `Maintenance` с причиной.
4. Оператор добавляет короткий комментарий или `Inspection`.
5. Если автомобиль исправен, обслуживание закрывается.
6. Maintenance Service публикует `MaintenanceCompleted`.
7. Fleet Service возвращает автомобиль в `Available`.

В этом сервисе не нужны сервисные станции, заказы на ремонт, склад запчастей, расписание мастеров и сложные статусы работ. Достаточно знать, почему машина была недоступна и когда ее вернули в парк.

### Insurance Service

Insurance Service отвечает за страховые полисы и страховые случаи. На первом этапе его можно оставить внутри монолита или Fleet/Admin-контура, если страховая логика простая.

Типичный поток:

1. Для автомобиля создается или обновляется страховой полис.
2. Сервис отслеживает срок действия полиса.
3. При ДТП или серьезном инциденте создается страховой случай.
4. Страховой случай связывается с автомобилем, поездкой и клиентом.
5. Оператор обновляет статус рассмотрения.

Insurance Service не должен управлять ремонтом автомобиля и не должен начислять оплату клиенту. Если по страховому случаю нужно создать начисление или компенсацию, это должно идти через Billing/Payments Service.

### Review/Feedback Service

Review/Feedback Service отвечает за отзывы, жалобы и обращения в поддержку. Он помогает операторам видеть проблемы клиентов, но не должен напрямую менять поездки, счета или автомобили без отдельного бизнес-действия.

Типичный поток:

1. Клиент оставляет отзыв или жалобу после поездки.
2. Review/Feedback Service сохраняет `Review`, `Complaint` или `SupportTicket`.
3. Оператор рассматривает обращение.
4. Если жалоба связана с повреждением автомобиля, оператор может создать осмотр или обслуживание.
5. Если жалоба связана с оплатой, оператор может передать вопрос в Billing/Payments.

Этот сервис полезен для клиентского опыта, но его не нужно выносить одним из первых.

### Media/File Service

Media/File Service отвечает за файлы и объектное хранилище. Он принимает файлы, кладет их в MinIO/S3-compatible storage и возвращает идентификатор файла.

Типичный поток загрузки документа:

1. Клиент загружает водительские права.
2. Мобильное приложение отправляет файл в Media/File Service.
3. Media/File Service сохраняет файл в MinIO.
4. Сервис создает `FileObject`.
5. Сервис возвращает `FileId`.
6. Customer/Profile Service сохраняет `FileId` в `ClientDocument`.

Типичный поток фото автомобиля:

1. Администратор загружает фото автомобиля.
2. Media/File Service сохраняет файл.
3. Fleet Service связывает `FileId` с автомобилем.

Media/File Service не должен решать, одобрен документ или нет, исправен автомобиль или нет, является ли фото доказательством штрафа. Он хранит файл и метаданные.

### Admin/Backoffice Service

Admin/Backoffice Service отвечает за административные действия, аудит, комментарии операторов и ручные корректировки. В простой версии это может быть не отдельный сервис, а админский интерфейс поверх API других сервисов.

Типичный поток:

1. Оператор выполняет действие: блокирует клиента, подтверждает документ, добавляет комментарий или вручную корректирует данные.
2. Admin/Backoffice Service сохраняет `AdminAction` или `AuditLog`.
3. Целевой сервис выполняет бизнес-действие через свой API.
4. В системе остается история, кто и почему сделал изменение.

Backoffice не должен обходить доменные сервисы и напрямую править их таблицы. Даже админские действия должны проходить через публичные команды соответствующего сервиса.

### API Gateway

API Gateway не является доменным микросервисом, но является входной точкой для мобильного приложения и админки.

Он выполняет технические задачи:

- маршрутизирует запросы в нужный сервис;
- проверяет JWT;
- добавляет или прокидывает correlation id;
- скрывает внутренние адреса сервисов;
- может ограничивать частоту запросов.

Пример:

- `GET /api/cars` уходит во Fleet Service;
- `POST /api/bookings` уходит в Booking/Trip Service;
- `POST /api/files` уходит в Media/File Service.

Gateway не должен содержать бизнес-логику. Он только маршрутизирует и применяет общие технические правила.

### RabbitMQ

RabbitMQ не является микросервисом, но связывает сервисы через события. Он нужен, чтобы сервисы не зависели друг от друга напрямую в бизнес-процессах.

Пример событийной цепочки:

1. Booking/Trip Service публикует `TripFinished`.
2. Billing/Payments Service создает счет.
3. Billing/Payments Service публикует `BillIssued`.
4. Notification Worker отправляет уведомление.
5. После оплаты Billing/Payments Service публикует `PaymentSucceeded`.
6. Notification Worker отправляет чек или уведомление об оплате.

Если Notification Worker временно недоступен, поездка и счет не должны ломаться. Событие останется в очереди или будет повторено по retry policy.

- `BookingsService`

### Основные правила

- нельзя бронировать недоступный автомобиль;
- бронь имеет TTL, например 15 минут;
- клиент не может иметь две активные брони;
- при создании брони автомобиль должен стать недоступным для других клиентов;
- при истечении брони автомобиль должен быть освобожден;
- `ReservationLock` должен иметь короткий TTL и освобождаться после успешного создания, отмены или истечения брони;
- `BookingExpiration` должен обрабатываться worker-ом или фоновой задачей идемпотентно, чтобы повторная обработка не ломала статус брони и автомобиля.

## Аппаратный контур для дипломного проекта

Для дипломного проекта в качестве бортового устройства автомобиля используется связка:

- ESP32 DevKit V4;
- NEO-6M GPS;
- SIM800L GSM/GPRS;
- SN65HVD230 CAN transceiver.

Эта связка позволяет показать реалистичный IoT-контур каршеринга: получение координат, передачу телеметрии в backend, прием команд от сервера и потенциальную интеграцию с CAN-шиной автомобиля.

## Роли компонентов

### ESP32 DevKit V4

ESP32 выступает главным контроллером бортового устройства.

Задачи ESP32:

- читать координаты от NEO-6M;
- читать данные с CAN-шины через SN65HVD230;
- управлять GSM/GPRS-модемом SIM800L;
- формировать telemetry packet;
- отправлять данные в Telematics/IoT Service;
- принимать команды от backend;
- управлять исполнительными выходами макета, например реле открытия/закрытия;
- хранить device id, настройки и состояние последней отправки;
- выполнять heartbeat.

Рекомендуемые интерфейсы:

- UART для NEO-6M;
- UART для SIM800L;
- CAN/TWAI интерфейс ESP32 для SN65HVD230;
- GPIO для реле, светодиодов и сервисных сигналов.

### NEO-6M

NEO-6M отвечает за получение GPS-координат.

Данные, которые нужны backend:

- latitude;
- longitude;
- speed;
- altitude, если доступно;
- satellites count;
- fix quality;
- GPS timestamp.

Эти данные используются:

- для отображения автомобиля на карте;
- для обновления местоположения в Fleet Service;
- для маршрута поездки в Trip Service;
- для dangerous driving в Fine/Violation Service;
- для контроля выезда из разрешенной зоны.

### SIM800L

SIM800L отвечает за передачу данных через мобильную сеть.

Варианты обмена:

- MQTT поверх TCP/GPRS;
- HTTP POST на Telematics/IoT Service;
- SMS как резервный аварийный канал.

Для диплома лучше выбрать основной вариант MQTT или HTTP:

- MQTT лучше показывает IoT-архитектуру и команды от сервера;
- HTTP проще для реализации и отладки.

Рекомендуемый вариант для проекта: MQTT, если времени достаточно. Если нужно быстрее и надежнее защитить дипломную реализацию, можно начать с HTTP POST и потом добавить MQTT как развитие.

### SN65HVD230

SN65HVD230 нужен как CAN transceiver между ESP32 и CAN-шиной.

В дипломном макете через него можно показать:

- чтение скорости автомобиля;
- чтение оборотов двигателя;
- чтение уровня топлива, если есть источник CAN-данных;
- чтение состояния зажигания;
- чтение диагностических данных;
- отправку тестовых CAN-фреймов на стенде.

Если реального автомобиля или CAN-стенда нет, можно использовать второй контроллер или CAN-генератор, который будет имитировать автомобильные сообщения.

## Схема обмена данными

```text
NEO-6M GPS
    |
    | UART
    v
ESP32 DevKit V4 <--- CAN/TWAI ---> SN65HVD230 <--- CAN bus / test stand
    |
    | UART AT commands
    v
SIM800L
    |
    | GPRS
    v
Telematics/IoT Service
    |
    | events
    v
Fleet Service / Trip Service / Fine Service / Notification Service
```

## Dangerous driving на базе ESP32

С указанными модулями можно реализовать базовые признаки опасного вождения:

- превышение скорости по GPS или CAN;
- резкое торможение по разнице скорости за короткий интервал;
- резкое ускорение по разнице скорости;
- движение вне разрешенной геозоны;
- движение после завершения поездки;
- потеря связи с устройством во время активной поездки.

Для более точного определения резких маневров желательно добавить IMU-модуль, например MPU6050 или MPU9250. Без IMU dangerous driving все равно можно показать на дипломе через анализ скорости GPS/CAN, но точность резких поворотов и ударов будет ограничена.

## Практическая реализация для диплома

Рекомендуемый минимальный сценарий:

1. ESP32 получает координаты от NEO-6M.
2. ESP32 получает скорость или тестовые CAN-данные через SN65HVD230.
3. ESP32 отправляет telemetry packet через SIM800L.
4. Telematics/IoT Service сохраняет телеметрию.
5. Fleet Service обновляет последнюю позицию автомобиля.
6. Trip Service добавляет точку маршрута к активной поездке.
7. Fine/Violation Service проверяет превышение скорости.
8. При нарушении создается `DangerousDrivingEvent`.
9. Fine/Violation Service создает штраф.
10. Billing Service добавляет штраф к счету поездки.

## Ограничения аппаратного макета

- SIM800L требует стабильного питания с достаточным током, иначе модем будет перезагружаться при передаче.
- NEO-6M может долго получать первый GPS fix в помещении.
- SN65HVD230 требует корректной CAN-шины или тестового генератора CAN-фреймов.
- Без IMU нельзя надежно определять удары и резкие повороты.
- Для реального автомобиля нужны гальваническая развязка, защита питания, автомобильный корпус и безопасная логика управления.

## Сущности и поля

Этот раздел описывает целевую модель данных микросервисов. Поля можно уточнять при проектировании конкретных API и миграций, но границы владения сущностями должны оставаться такими: сервис владеет своими сущностями и не дает другим сервисам напрямую менять свою базу.

Для доменной модели лучше закрывать прямую запись в поля через `private set`/закрытые конструкторы и менять состояние через явные методы. Блоки `Доменные методы и проверки` ниже не являются окончательным публичным API, а задают направление: `Create(...)` собирает обязательные инварианты при создании, а update-методы показывают, какие изменения стоит делать через поведенческие методы сущности вместо произвольного изменения свойств.

Не нужно делать один полный `Update(...)` для каждой сущности и не обязательно перечислять отдельный update-метод для каждого поля. В целевой реализации лучше оставлять только те методы изменения, которые отражают реальные бизнес-действия, требуют проверки инвариантов, меняют статус/жизненный цикл, публикуют доменные события или важны для аудита. Если несколько полей меняются вместе по одному бизнес-сценарию, их можно объединять в один метод, например `UpdateInfo(name, description, sortOrder)`, `UpdateRegistration(vin, licensePlate)` или `UpdateLocation(locationText, location)`. Если поля меняются независимо и имеют разный смысл, лучше оставить отдельные поведенческие методы, например `ChangeStatus(status)`, `AssignTariff(tariffId)`, `Activate()`/`Deactivate()`. Технические, неизменяемые и системные поля (`Id`, `CreatedAt`, `CreatedBy`, вычисляемые значения, внешние read-only ссылки) не должны обновляться через публичные update-методы без отдельной бизнес-причины.

## Межсервисное взаимодействие

### Синхронное взаимодействие

Синхронные запросы допустимы для чтения или быстрых проверок:

- мобильное приложение -> API Gateway -> нужный сервис;
- админка -> API Gateway -> нужный сервис;
- сервис -> сервис только для read-only запросов или проверок, которые не создают распределенную транзакцию.

### Асинхронное взаимодействие

Бизнес-процессы должны строиться через события:

- `TripFinished` -> Billing Service создает счет;
- `DangerousDrivingDetected` -> Fine/Violation Service создает нарушение;
- `FineCreated` -> Billing Service добавляет начисление;
- `BillIssued` -> Notification Service отправляет уведомление;
- `PaymentSucceeded` -> Billing Service закрывает счет;
- `CarLocationUpdated` -> Fleet Service обновляет последнюю позицию;
- `BookingCreated` -> Fleet Service резервирует авто;
- `BookingExpired` -> Fleet Service освобождает авто.

### Надежность сообщений

Минимальный набор для надежности сообщений:

- Outbox table для producers критичных событий;
- retry policy;
- dead-letter queue;
- idempotency key для платежей, бронирования и команд к автомобилю;
- event version;
- correlation id.

Inbox table и causation id можно добавить позже для consumers, где реально есть риск повторной обработки с побочными эффектами.

## Ключевые бизнес-сценарии

### Регистрация и допуск клиента

1. Клиент регистрируется в Identity Service.
2. Identity Service публикует `UserRegistered`.
3. Customer/Profile Service создает профиль клиента.
4. Клиент загружает документы через Media/File Service.
5. Customer/Profile Service отправляет документы на проверку.
6. Администратор подтверждает документы.
7. Customer/Profile Service публикует `CustomerVerified`.
8. Notification Service отправляет уведомление клиенту.

### Бронирование автомобиля

1. Клиент выбирает автомобиль.
2. Booking Service проверяет активные брони клиента.
3. Booking Service запрашивает доступность автомобиля или использует локальную read model.
4. Booking Service создает бронь.
5. Booking Service публикует `BookingCreated`.
6. Fleet Service помечает автомобиль как зарезервированный.
7. Notification Service отправляет подтверждение.

### Старт поездки

1. Клиент нажимает "Начать поездку".
2. Trip Service проверяет активную бронь.
3. Trip Service создает поездку.
4. Trip Service публикует `TripStarted`.
5. Telematics/IoT Service отправляет команду открыть автомобиль.
6. Fleet Service меняет статус автомобиля.
7. Booking Service закрывает бронь как подтвержденную.

### Dangerous driving и штраф

1. Микроконтроллер отправляет телеметрию.
2. Telematics/IoT Service принимает данные.
3. Telematics/IoT Service обнаруживает резкое торможение, превышение скорости или удар.
4. Telematics/IoT Service публикует событие dangerous driving.
5. Fine/Violation Service создает нарушение.
6. Fine/Violation Service применяет правила штрафов.
7. При необходимости штраф уходит на ручную модерацию.
8. Fine/Violation Service публикует `FineCreated`.
9. Billing Service добавляет начисление к счету поездки.
10. Notification Service уведомляет клиента.

### Завершение поездки и оплата

1. Клиент завершает поездку.
2. Trip Service фиксирует время, координаты, пробег и состояние автомобиля.
3. Trip Service публикует `TripFinished`.
4. Pricing/Tariff Service рассчитывает стоимость.
5. Billing Service создает счет.
6. Billing Service добавляет штрафы, скидки и дополнительные начисления.
7. Billing Service публикует `BillIssued`.
8. Payment Gateway Service создает платеж.
9. Клиент оплачивает счет.
10. Payment Gateway Service получает webhook.
11. Payment Gateway Service публикует `PaymentSucceeded`.
12. Billing Service закрывает счет.
13. Notification Service отправляет чек.
14. Fleet Service возвращает автомобиль в доступность или отправляет на обслуживание.

## Этапы миграции

### Этап 1. Подготовка монолита

- Зафиксировать bounded contexts внутри текущего решения.
- Убрать прямые зависимости между доменами там, где это возможно.
- Вынести общие DTO событий в отдельный проект.
- Добавить correlation id.
- Добавить structured logging.
- Добавить health checks.
- Подготовить API versioning.

### Этап 2. Инфраструктура

- Добавить API Gateway.
- Добавить брокер сообщений для ключевых событий.
- Добавить PostgreSQL-схемы под будущие сервисы.
- Добавить MinIO, если файловая логика уже используется.
- Добавить базовый Outbox только там, где событие критично: бронь, поездка, счет, платеж.
- Оставить Redis, OpenTelemetry и централизованные логи как следующий шаг, если они реально нужны.

### Этап 3. Первый физический сервис

Первым физическим сервисом можно вынести Media/File Service или Identity Service.

Media/File Service проще и безопаснее, потому что он слабо связан с бизнес-логикой. Identity Service значимее архитектурно, но затрагивает авторизацию всех API. Для более спокойной миграции лучше начать с Media/File Service, затем вынести Identity.

Что сделать:

- создать первый отдельный API;
- подключить его к gateway;
- выделить собственную схему или базу;
- заменить прямые вызовы в монолите на HTTP/API-клиент;
- оставить остальную бизнес-логику в монолите.

### Этап 4. Media/File Service

Если Media/File Service не был вынесен на предыдущем этапе, вынести работу с MinIO/S3:

- фото автомобилей;
- документы клиентов;
- доказательства штрафов;
- фото поездок.

Этот сервис относительно слабо связан с бизнес-логикой, поэтому подходит для раннего выноса.

### Этап 5. Identity Service

Вынести пользователей, вход, роли и токены.

Что сделать:

- создать `Carsharing.Identity.Api`;
- перенести `User`, auth logic и JWT;
- обновить API Gateway;
- оставить остальные сервисы и монолит потребителями токенов.

На первом этапе можно не делать сложную permission-модель и полный audit login.

### Этап 6. Fleet Service

Вынести автомобили, категории, характеристики, статусы и координаты.

Важно:

- не давать другим сервисам менять таблицы автомобилей напрямую;
- все изменения доступности автомобиля должны идти через Fleet Service или события.
- геоданные хранить через PostGIS/NetTopologySuite, а наружу отдавать DTO с широтой и долготой для клиента.

### Этап 7. Booking/Trip Service

Вынести бронирования и поездки одним сервисом. Это проще, чем сразу делить Booking Service и Trip Service, потому что бронь и поездка тесно связаны одним жизненным циклом аренды.

Основной риск:

- гонки при бронировании одного автомобиля двумя клиентами.

Решение:

- атомарное изменение доступности автомобиля;
- optimistic concurrency или уникальный индекс на активную бронь;
- idempotency key;
- событие `CarReserved`.

Booking/Trip Service должен владеть жизненным циклом аренды, но не должен сам проводить оплату или создавать штрафы.

### Этап 8. Billing/Payments Service

На первом этапе счета и платежи можно держать вместе. Отдельный Payment Gateway Service нужен позже, когда появится реальная интеграция с провайдером, webhooks, refunds и несколько платежных методов.

Billing/Payments Service должен слушать:

- `TripFinished`;
- `FineCreated`, если штрафы уже вынесены;
- `PaymentSucceeded`;
- `PaymentFailed`.

Важно:

- платежи должны быть идемпотентными;
- повторный callback не должен создавать двойную оплату;
- счет нельзя считать оплаченным без подтверждения платежа.

### Этап 9. Notification Worker

Сначала это может быть worker, а не полноценный отдельный API-сервис.

Что сделать:

- слушать события из RabbitMQ;
- отправлять email/SMS/push-заглушки;
- хранить историю отправки.

### Этап 10. Telematics/IoT Service

Добавить контур микроконтроллера:

- MQTT broker;
- прием телеметрии;
- команды к автомобилю;
- heartbeat;
- обработка offline-состояний;
- device certificates как усиление безопасности, когда базовый обмен уже работает.

### Этап 11. Fine/Violation Service

Вынести штрафы и dangerous driving.

Fine/Violation Service должен принимать события от Telematics/IoT Service и создавать штрафы по правилам.

### Этап 12. Payment Gateway Service

Выделить из Billing/Payments Service отдельный Payment Gateway Service, когда появится реальный платежный провайдер.

Важно:

- все webhooks должны быть идемпотентными;
- нельзя доверять webhook без проверки подписи;
- нельзя считать счет оплаченным до подтверждения провайдера.

### Этап 13. Остальные сервисы

Вынести:

- Maintenance Service;
- Insurance Service;
- Review/Feedback Service;
- Admin/Backoffice Service.

### Этап 14. Финальное разделение

- У каждого сервиса своя БД.
- Общая БД монолита больше не используется.
- Все интеграции идут через API или события.
- Добавлены contract tests для стабильных контрактов.
- Добавлены end-to-end тесты критичных сценариев.

## Что не нужно делать сразу

- Не нужно сразу разрезать весь монолит на 15 сервисов.
- Не нужно делать распределенные транзакции между сервисами.
- Не нужно сразу поднимать отдельную базу под каждый сервис; можно начать с отдельных PostgreSQL-схем.
- Не нужно оставлять общую базу данных для всех сервисов как постоянное решение.
- Не нужно создавать общий `Shared.Domain` с бизнес-сущностями всех сервисов.
- Не нужно позволять сервисам напрямую менять данные друг друга.

## Первый практический шаг

Первый технический шаг:

1. Создать проект `Carsharing.Contracts`.
2. Описать первые интеграционные события:
   - `CarReserved`
   - `BookingCreated`
   - `TripFinished`
   - `BillIssued`
   - `PaymentSucceeded`
3. Добавить correlation id.
4. Добавить RabbitMQ в `docker-compose`.
5. Добавить базовый Outbox для публикации `TripFinished` и `BillIssued`.
6. Первым вынести Media/File Service или Identity Service.

### Как читать эту структуру

- `src/Contracts/Carsharing.Contracts` содержит только стабильные публичные контракты: события, общие результаты, claims, options и небольшие middleware. Туда нельзя переносить EF-сущности, бизнес-сервисы и репозитории конкретных сервисов.
- `src/Contracts/Carsharing.ServiceDefaults` содержит технические строительные блоки: health checks, correlation id, базовую публикацию событий, outbox/inbox и общую настройку observability. Это аналог общего инфраструктурного слоя, но без бизнес-логики.
- `src/Gateway/Carsharing.ApiGateway` отвечает только за маршрутизацию, авторизацию на входе, correlation id и агрегацию простых маршрутов. Он не должен напрямую ходить в базы данных сервисов.
- `src/Services/<ServiceName>/<ServiceName>.Api` содержит HTTP API, controllers, filters, настройки DI и Dockerfile сервиса.
- `src/Services/<ServiceName>/<ServiceName>.Application` содержит use cases, DTO, validators, mapping profiles, application services и обработчики интеграционных событий.
- `src/Services/<ServiceName>/<ServiceName>.Domain` содержит бизнес-сущности, enum, domain events, domain policies, repository interfaces и спецификации только этого bounded context.
- `src/Services/<ServiceName>/<ServiceName>.Infrastructure` содержит EF Core DbContext, миграции, repository implementations, consumers/publishers, внешние клиенты и реализации технических интерфейсов.
- `src/Tests` разделен на contract, integration и end-to-end тесты, чтобы не смешивать проверку контрактов с полными сценариями.
- `deploy` и `scripts` нужны для повторяемого локального запуска и дальнейшего перехода от Docker Compose к Kubernetes.

### Минимальная структура для первого выделенного сервиса

Если начинать с малого, для первого сервиса не обязательно сразу создавать все сервисы из дерева выше. Достаточно повторить один вертикальный срез:
