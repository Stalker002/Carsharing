# Облегченный план перехода Carsharing на микросервисы

## Цель

Сделать переход от текущего .NET-монолита к микросервисной архитектуре без уровня сложности enterprise-системы. План сохраняет достойный архитектурный уровень: четкие границы ответственности, постепенное выделение сервисов, события для важных бизнес-процессов и возможность развивать систему дальше.

Главная идея: сначала привести монолит к модульной структуре, затем вынести только самые полезные сервисы. Не нужно сразу делать 10-15 сервисов, Kubernetes, сложные Saga, отдельную observability-платформу и полный набор enterprise-паттернов.

## Принципы упрощенного подхода

- Не переписывать систему с нуля.
- Не выделять сервис, если его граница пока неочевидна.
- Начать с 4-6 сервисов вместо полного разбиения.
- Оставить Docker Compose как основную среду запуска.
- Использовать REST для простых синхронных запросов.
- Использовать RabbitMQ только для событий, где нужна слабая связность.
- Ввести отдельные базы данных постепенно, а не в первый день.
- Не делать общий `Shared.Domain` с бизнес-сущностями всех сервисов.
- Общими могут быть только контракты, базовые DTO, события и технические утилиты.

## Что оставить проще

В полной микросервисной архитектуре часто требуют отдельные сервисы для identity, profile, fleet, booking, trip, billing, payments, fines, telematics, notifications, media, backoffice, insurance, maintenance и других зон.

В облегченном варианте на первом этапе достаточно таких блоков:

1. `Identity Service`
2. `Fleet Service`
3. `Booking/Trip Service`
4. `Billing/Payments Service`
5. `Media Service`
6. `Notification Worker`

Некоторые зоны можно оставить внутри монолита или объединить:

- `Client`, `ClientDocument`, `Favorite` можно сначала держать рядом с Identity или в монолите.
- `Booking` и `Trip` можно вынести одним сервисом, потому что они тесно связаны жизненным циклом аренды.
- `Billing` и `Payment` можно сначала держать вместе, если нет реального внешнего платежного провайдера.
- `Fine`, `Insurance`, `Maintenance`, `Review`, `Promocode`, `Tariff` можно не выносить первыми.
- `Telematics/IoT` можно сделать отдельным контуром позже, когда появится стабильный сценарий с устройством.

## Целевая архитектура первого уровня

```text
Mobile App / Web Admin
        |
        v
API Gateway
        |
        +--> Identity Service
        +--> Fleet Service
        +--> Booking/Trip Service
        +--> Billing/Payments Service
        +--> Media Service
        |
        v
RabbitMQ
        |
        +--> Notification Worker
```

На этом уровне система уже выглядит как микросервисная, но остается управляемой:

- один gateway;
- несколько понятных сервисов;
- один брокер сообщений;
- Docker Compose;
- PostgreSQL;
- MinIO для файлов;
- простые health checks и логи.

## Минимальный технический стек

- Backend: `.NET`, `ASP.NET Core`, `Entity Framework Core`.
- API Gateway: `YARP`.
- Database: `PostgreSQL`.
- Broker: `RabbitMQ`.
- Files: `MinIO`.
- Cache: `Redis`, только если реально нужен.
- Logs: стандартные structured logs в консоль и файл, без обязательного Loki/Grafana.
- Observability: health checks и correlation id на первом этапе.
- Запуск: `Docker Compose`.

## Что обязательно сделать даже в облегченной версии

- Разделить ответственность между доменными областями.
- Не обращаться напрямую к таблицам другого сервиса после его выделения.
- Версионировать публичные API или хотя бы не ломать контракты без явной причины.
- Добавить correlation id для запросов.
- Сделать идемпотентность для платежей и критичных команд.
- Логировать важные бизнес-события: регистрация, бронь, старт поездки, завершение поездки, оплата.
- Покрыть тестами основные сценарии: бронирование, старт поездки, завершение поездки, оплата.

## Что не обязательно делать сразу

- Kubernetes.
- Kafka.
- Полный Outbox/Inbox во всех сервисах.
- Сложные Saga.
- gRPC.
- Service Mesh.
- Centralized tracing.
- Contract tests для всех контрактов.
- Отдельная база данных для каждого сервиса с первого дня.
- Полный backoffice как отдельный сервис.
- Отдельный сервис для каждой сущности.

Эти вещи можно добавить позже, если проект реально дорастет до такой сложности.

## Сервисы первого этапа

### 1. Identity Service

Отвечает за пользователей, вход, регистрацию, роли и токены.

Что перенести:

- `User`
- авторизацию;
- регистрацию;
- выдачу JWT;
- refresh tokens, если они уже используются или планируются.

Что можно пока не выносить:

- сложную систему permissions;
- audit login;
- отдельную KYC-логику;
- управление документами клиента.

События:

- `UserRegistered`
- `UserBlocked`
- `UserRoleChanged`

### 2. Fleet Service

Отвечает за автомобили, категории, статусы, фотографии и базовую доступность.

Что перенести:

- `Car`
- `Category`
- `CarStatus`
- `SpecificationCar`
- базовую работу с фото автомобилей.

Что важно:

- другие сервисы не должны напрямую менять статус автомобиля;
- бронирование должно менять доступность через API или событие;
- текущие координаты автомобиля можно хранить здесь, даже если телематика пока простая.

События:

- `CarCreated`
- `CarStatusChanged`
- `CarReserved`
- `CarReleased`

### 3. Booking/Trip Service

Объединенный сервис для бронирования и поездок. Это проще, чем сразу делить бронь и поездку на два сервиса.

Что перенести:

- `Booking`
- `BookingStatus`
- `Trip`
- `TripStatus`
- `TripDetail`

Основные правила:

- клиент не может иметь две активные брони;
- автомобиль нельзя забронировать дважды;
- бронь должна иметь срок действия;
- поездка стартует только из активной брони;
- поездка завершается с фиксацией времени, стоимости и состояния.

События:

- `BookingCreated`
- `BookingCancelled`
- `BookingExpired`
- `TripStarted`
- `TripFinished`

### 4. Billing/Payments Service

Объединенный сервис для счетов и платежей. На старте это практичнее, чем сразу выделять отдельный Payment Gateway Service.

Что перенести:

- `Bill`
- `BillStatus`
- `Payment`
- базовый расчет задолженности;
- отметку об оплате.

Что важно:

- платеж должен быть идемпотентным;
- повторный callback от платежной системы не должен создавать двойную оплату;
- счет должен иметь понятные статусы: `Created`, `PendingPayment`, `Paid`, `Failed`, `Cancelled`.

События:

- `BillIssued`
- `PaymentStarted`
- `PaymentSucceeded`
- `PaymentFailed`

### 5. Media Service

Сервис для файлов: документы клиентов, фото автомобилей, фото поездок и доказательства штрафов.

Что перенести:

- загрузку файлов;
- хранение в MinIO;
- выдачу ссылок;
- базовую привязку файла к сущности.

Почему стоит вынести рано:

- сервис слабо связан с бизнес-логикой;
- помогает убрать файловую логику из доменных сервисов;
- хорошо демонстрирует самостоятельную границу микросервиса.

### 6. Notification Worker

На первом этапе это может быть не полноценный API-сервис, а worker, который слушает события и отправляет уведомления.

Что делает:

- отправляет email/SMS/push-заглушки;
- реагирует на регистрацию, бронь, завершение поездки и оплату;
- пишет историю отправки уведомлений.

События:

- `UserRegistered`
- `BookingCreated`
- `TripFinished`
- `BillIssued`
- `PaymentSucceeded`

## Упрощенный порядок миграции

### Этап 1. Подготовить монолит

- Разложить код по доменным зонам внутри текущего решения.
- Убрать лишние прямые зависимости между сервисами приложения.
- Выделить контракты запросов, ответов и событий.
- Добавить correlation id.
- Добавить health checks.
- Настроить структурированные логи.

Результат: система еще монолитная, но уже готова к аккуратному разрезанию.

### Этап 2. Добавить инфраструктурный минимум

- Добавить `YARP` как API Gateway.
- Добавить RabbitMQ в `docker-compose`.
- Добавить MinIO, если файловая логика уже есть.
- Добавить отдельный проект с контрактами: `Carsharing.Contracts`.

Результат: появляется основа для выделения сервисов.

### Этап 3. Вынести Media Service

Это самый безопасный первый сервис.

Что сделать:

- создать отдельный API для загрузки файлов;
- перенести работу с MinIO;
- заменить прямую файловую логику в монолите на вызов Media Service;
- оставить бизнес-сущности в монолите.

Результат: первый реальный сервис без большого риска для бизнес-логики.

### Этап 4. Вынести Identity Service

Что сделать:

- создать отдельный сервис авторизации;
- перенести пользователей и токены;
- настроить gateway;
- оставить остальные домены потребителями JWT.

Результат: авторизация становится отдельной границей.

### Этап 5. Вынести Fleet Service

Что сделать:

- перенести автомобили, категории и статусы;
- дать Booking/Trip Service или монолиту API для проверки доступности;
- запретить прямое изменение автомобилей из других сервисов.

Результат: парк автомобилей управляется отдельно.

### Этап 6. Вынести Booking/Trip Service

Что сделать:

- перенести брони и поездки;
- добавить защиту от двойного бронирования;
- публиковать события `TripStarted` и `TripFinished`;
- после завершения поездки отправлять событие в Billing/Payments Service.

Результат: основной бизнес-процесс аренды становится отдельным сервисом.

### Этап 7. Вынести Billing/Payments Service

Что сделать:

- перенести счета и платежи;
- принимать `TripFinished`;
- создавать счет;
- фиксировать оплату;
- публиковать `PaymentSucceeded`.

Результат: финансовый контур отделен от поездок.

### Этап 8. Добавить Notification Worker

Что сделать:

- слушать события из RabbitMQ;
- отправлять заглушки уведомлений;
- хранить историю отправки.

Результат: события начинают приносить практическую пользу без усложнения ядра.

## Предлагаемая структура solution

```text
Carsharing.sln
src/
  BuildingBlocks/
    Carsharing.Contracts/
    Carsharing.SharedKernel/
  Gateway/
    Carsharing.ApiGateway/
  Services/
    Identity/
      Carsharing.Identity.Api/
    Fleet/
      Carsharing.Fleet.Api/
    BookingTrips/
      Carsharing.BookingTrips.Api/
    BillingPayments/
      Carsharing.BillingPayments.Api/
    Media/
      Carsharing.Media.Api/
    Notifications/
      Carsharing.Notifications.Worker/
  Monolith/
    Carsharing.Api/
    Carsharing.Application/
    Carsharing.Core/
    Carsharing.DataAccess/
tests/
  Carsharing.Tests/
  Carsharing.IntegrationTests/
```

Для дипломного или учебного проекта можно не делать отдельные `Domain/Application/Infrastructure` проекты внутри каждого сервиса сразу. Достаточно держать чистую структуру папок внутри сервиса:

```text
Carsharing.Fleet.Api/
  Controllers/
  Contracts/
  Data/
  Models/
  Services/
```

Когда сервис станет большим, его можно разделить на слои.

## Минимальный набор событий

На старте достаточно описать такие события:

- `UserRegistered`
- `CarReserved`
- `CarReleased`
- `BookingCreated`
- `BookingCancelled`
- `TripStarted`
- `TripFinished`
- `BillIssued`
- `PaymentSucceeded`

Каждое событие должно иметь базовые поля:

```text
EventId
EventType
OccurredAt
CorrelationId
Version
Payload
```

## Базы данных

### Упрощенный вариант

На первом этапе можно использовать одну PostgreSQL-инстанцию и разные схемы:

- `identity`
- `fleet`
- `booking_trips`
- `billing_payments`
- `media`
- `notifications`

Это проще в разработке и демонстрации, но важно соблюдать правило: сервис работает только со своей схемой.

### Более зрелый вариант

Когда сервисы стабилизируются, можно перейти к отдельным базам:

- `carsharing_identity`
- `carsharing_fleet`
- `carsharing_booking_trips`
- `carsharing_billing_payments`
- `carsharing_media`

Такой переход уже будет техническим, а не архитектурным.

## Уровни зрелости

### Уровень 1. Модульный монолит

- домены разделены внутри кода;
- есть контракты;
- нет прямого смешивания бизнес-логики;
- сервисы еще физически не вынесены.

Это нормальная стартовая точка.

### Уровень 2. Гибридная архитектура

- часть функций осталась в монолите;
- Media, Identity или Fleet уже вынесены;
- gateway маршрутизирует запросы;
- RabbitMQ используется для нескольких событий.

Это хороший уровень для учебного проекта и первой production-версии.

### Уровень 3. Облегченные микросервисы

- основные сервисы физически разделены;
- у каждого сервиса своя схема или база;
- критичные процессы работают через события;
- есть health checks, логи, correlation id и интеграционные тесты.

Это достойный уровень без enterprise-перегруза.

### Уровень 4. Enterprise-уровень

Этот уровень не является целью текущего плана.

Он включает:

- Kubernetes;
- полную observability-платформу;
- contract testing для всех сервисов;
- outbox/inbox во всех сервисах;
- сложные Saga;
- service mesh;
- централизованное управление секретами;
- autoscaling;
- отдельные команды владения сервисами.

К этому можно прийти позже, но не нужно начинать с этого.

## Риски и как их снизить

### Риск: сервисов станет слишком много

Решение: не выделять сервис без понятного владельца данных и бизнес-процесса.

### Риск: появятся распределенные транзакции

Решение: сначала объединять тесно связанные зоны, например `Booking` и `Trip`, `Billing` и `Payment`.

### Риск: сервисы начнут читать чужие таблицы

Решение: даже при общей PostgreSQL-инстанции использовать разные схемы и запретить cross-schema доступ в коде.

### Риск: RabbitMQ усложнит разработку

Решение: использовать брокер только для событий, где он реально нужен. Простые чтения оставить через REST.

### Риск: миграция затянется

Решение: после каждого этапа оставлять систему рабочей, не начинать следующий сервис до стабилизации предыдущего.

## Что можно показать как результат

Для достойной защиты или демонстрации достаточно показать:

- API Gateway;
- 3-4 выделенных сервиса;
- RabbitMQ для событий;
- MinIO для файлов;
- отдельные схемы или базы;
- Docker Compose;
- сценарий бронирования и поездки;
- сценарий создания счета после завершения поездки;
- уведомление после оплаты;
- логи с correlation id.

Такой результат выглядит как настоящая микросервисная архитектура, но не требует enterprise-инфраструктуры.

## Первый практический шаг

Самый разумный старт:

1. Создать `Carsharing.Contracts`.
2. Описать базовые события:
   - `BookingCreated`
   - `TripFinished`
   - `BillIssued`
   - `PaymentSucceeded`
3. Добавить correlation id.
4. Подключить RabbitMQ в `docker-compose`.
5. Вынести Media Service или Identity Service первым.

Если нужно минимизировать риск, первым лучше вынести `Media Service`. Если нужно показать более значимую бизнес-границу, первым можно вынести `Identity Service`.
