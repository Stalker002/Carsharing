# Техническое задание на прошивку ESP32 для телематики Carsharing

## 1. Назначение

Разработать прошивку для ESP32, которая будет работать как бортовое телематическое устройство автомобиля в будущей микросервисной архитектуре Carsharing.

Прошивка должна:

- собирать техническую телеметрию автомобиля и устройства;
- передавать данные в backend через `Telematics/IoT Service`;
- принимать команды от backend и безопасно исполнять их;
- работать устойчиво при потере сети, перезагрузках и временной недоступности брокера;
- не содержать бизнес-логики каршеринга: бронирования, оплаты, штрафов, тарифов и прав доступа.

## 2. Цели проекта

Основные цели:

- подготовить устройство к интеграции с микросервисами через MQTT;
- отделить устройство от бизнес-сервисов и оставить на ESP32 только технический контур;
- обеспечить расширяемость под GPS, CAN/TWAI, реле дверей, блокировку двигателя, диагностику и OTA;
- заложить безопасную модель команд, конфигурации и обновлений.

Не цели первой версии:

- прямые HTTP-вызовы в Fleet, Booking, Trip, Billing, Fine или User Service;
- расчет стоимости поездки на устройстве;
- принятие решений о разрешении поездки на устройстве;
- хранение персональных данных клиента на устройстве;
- полноценная поддержка всех CAN ID реального автомобиля без отдельной карты сигналов.

## 3. Целевая архитектура

### 3.1. Роль ESP32

ESP32 является edge-устройством. Оно передает факты и исполняет команды.

Факты:

- координаты;
- скорость;
- уровень топлива или заряда, если доступен;
- состояние зажигания;
- состояние дверей и замков, если доступно;
- напряжение питания;
- качество связи;
- состояние прошивки;
- диагностические ошибки.

Команды:

- получить текущее состояние;
- открыть двери;
- закрыть двери;
- разрешить запуск двигателя;
- запретить запуск двигателя;
- изменить период отправки телеметрии;
- перезагрузить устройство;
- применить новую конфигурацию;
- запустить OTA-обновление, если включено.

### 3.2. Роль backend

ESP32 взаимодействует только с `Telematics/IoT Service` через MQTT broker.

`Telematics/IoT Service` отвечает за:

- регистрацию и идентификацию устройств;
- прием телеметрии;
- валидацию формата сообщений;
- публикацию доменных событий для остальных микросервисов;
- маршрутизацию команд на устройство;
- хранение состояния устройства;
- аудит команд и результатов их выполнения.

Остальные микросервисы получают данные не от ESP32 напрямую, а через события backend.

## 4. Аппаратная платформа

### 4.1. Базовая плата

- MCU: ESP32 DevKit V4 или совместимая плата на ESP32.
- Framework: Arduino Core for ESP32 или PlatformIO-проект на базе Arduino.
- Основной язык: C++.

### 4.2. Подключаемые модули

Минимальный стенд:

- ESP32 DevKit;
- GPS-модуль NEO-6M или совместимый UART GPS;
- реле или MOSFET-модули для центрального замка и аварийной сигнализации;
- светодиод статуса;
- делитель напряжения для контроля питания;
- Wi-Fi как основной транспорт для MVP.

Расширенный стенд:

- CAN-трансивер SN65HVD230 для TWAI/CAN;
- SIM800L/SIM7600 или другой GSM/LTE-модем для мобильной связи;
- внешний watchdog или power supervisor;
- защищенное питание от бортовой сети автомобиля.

### 4.3. Рекомендуемые пины MVP

| Назначение | GPIO |
| --- | --- |
| GPS RX | 17 |
| GPS TX | 16 |
| SIM800 RX | 27 |
| SIM800 TX | 26 |
| Lock relay / central lock IN1 | 18 |
| Unlock relay | 18 |
| Hazard relay IN2 | 19 |
| Engine relay | disabled |
| Status LED | 2 |
| Battery ADC | 34 |
| CAN TX | 4 |
| CAN RX | 5 |

Пины должны быть вынесены в конфигурационный файл и не должны быть жестко зашиты в бизнес-логике прошивки.

## 5. Сетевое взаимодействие

### 5.1. Основной транспорт

MVP:

- Wi-Fi;
- MQTT поверх TCP;
- JSON payload.

Production-ready версия:

- MQTT over TLS;
- уникальные учетные данные устройства;
- сертификаты устройства или иной механизм строгой идентификации;
- опционально GSM/LTE как основной или резервный канал.

### 5.2. MQTT topics

Базовые topics:

```text
cars/{carId}/telemetry
cars/{carId}/heartbeat
cars/{carId}/commands
cars/{carId}/command-results
cars/{carId}/diagnostics
cars/{carId}/events
```

Где:

- `carId` - идентификатор автомобиля в backend;
- `deviceId` - уникальный идентификатор устройства;
- `correlationId` - идентификатор связки запроса, команды и результата;
- `commandId` - уникальный идентификатор команды.

### 5.3. QoS

Рекомендуемая политика:

| Тип сообщения | QoS | Retain |
| --- | ---: | --- |
| telemetry | 0 или 1 | false |
| heartbeat | 0 | false |
| commands | 1 | false |
| command-results | 1 | false |
| diagnostics | 0 или 1 | false |
| config | 1 | true, если используется отдельный retained topic |

Для MVP допустимо использовать QoS 0 для телеметрии и QoS 1 для команд.

## 6. Форматы сообщений

### 6.1. Общие требования к JSON

Каждое исходящее сообщение должно содержать:

- `schemaVersion`;
- `deviceId`;
- `carId`;
- `messageId`;
- `sentAt`;
- полезную нагрузку по типу сообщения.

Время передается в UTC в ISO 8601, например:

```text
2026-05-23T12:30:00Z
```

Если точное время недоступно, прошивка должна передавать флаг `timeSynchronized: false`.

### 6.2. Telemetry

Topic:

```text
cars/{carId}/telemetry
```

Пример:

```json
{
  "schemaVersion": 1,
  "messageId": "tel-000001",
  "deviceId": "esp32-car-001",
  "carId": "car-001",
  "sentAt": "2026-05-23T12:30:00Z",
  "timeSynchronized": true,
  "location": {
    "lat": 53.9023,
    "lon": 27.5619,
    "accuracyMeters": 8.5,
    "satellites": 9
  },
  "vehicle": {
    "speedKmh": 42.5,
    "fuelPercent": 63,
    "ignitionOn": true,
    "doorsLocked": true,
    "engineBlocked": false
  },
  "device": {
    "batteryVoltage": 12.4,
    "rssi": -58,
    "uptimeSeconds": 3600,
    "freeHeapBytes": 120000,
    "firmwareVersion": "0.1.0"
  }
}
```

### 6.3. Heartbeat

Topic:

```text
cars/{carId}/heartbeat
```

Пример:

```json
{
  "schemaVersion": 1,
  "messageId": "hb-000001",
  "deviceId": "esp32-car-001",
  "carId": "car-001",
  "sentAt": "2026-05-23T12:30:00Z",
  "status": "Online",
  "firmwareVersion": "0.1.0",
  "network": {
    "transport": "WiFi",
    "rssi": -58,
    "mqttConnected": true
  }
}
```

### 6.4. Command

Topic:

```text
cars/{carId}/commands
```

Пример:

```json
{
  "schemaVersion": 1,
  "commandId": "cmd-001",
  "correlationId": "corr-001",
  "deviceId": "esp32-car-001",
  "carId": "car-001",
  "commandType": "UnlockDoors",
  "createdAt": "2026-05-23T12:30:00Z",
  "expiresAt": "2026-05-23T12:31:00Z",
  "payload": {}
}
```

Поддерживаемые команды MVP:

| commandType | Назначение |
| --- | --- |
| `GetState` | Немедленно отправить текущее состояние |
| `LockDoors` | Закрыть двери |
| `UnlockDoors` | Открыть двери |
| `EnableEngine` | Разрешить запуск двигателя |
| `DisableEngine` | Запретить запуск двигателя |
| `SetTelemetryInterval` | Изменить период отправки телеметрии |
| `RebootDevice` | Перезагрузить ESP32 |

Дополнительные команды для следующих версий:

| commandType | Назначение |
| --- | --- |
| `UpdateConfig` | Обновить конфигурацию устройства |
| `StartOtaUpdate` | Запустить OTA-обновление |
| `ResetFaults` | Сбросить локальные диагностические ошибки |
| `SetMaintenanceMode` | Перевести устройство в сервисный режим |

### 6.5. Command result

Topic:

```text
cars/{carId}/command-results
```

Пример успешного результата:

```json
{
  "schemaVersion": 1,
  "messageId": "res-000001",
  "commandId": "cmd-001",
  "correlationId": "corr-001",
  "deviceId": "esp32-car-001",
  "carId": "car-001",
  "sentAt": "2026-05-23T12:30:03Z",
  "status": "Succeeded",
  "result": {
    "doorsLocked": false
  }
}
```

Пример ошибки:

```json
{
  "schemaVersion": 1,
  "messageId": "res-000002",
  "commandId": "cmd-002",
  "correlationId": "corr-002",
  "deviceId": "esp32-car-001",
  "carId": "car-001",
  "sentAt": "2026-05-23T12:30:03Z",
  "status": "Failed",
  "error": {
    "code": "CommandExpired",
    "message": "Command expiration time has passed"
  }
}
```

### 6.6. Diagnostics

Topic:

```text
cars/{carId}/diagnostics
```

Прошивка должна отправлять диагностические сообщения при:

- старте устройства;
- перезагрузке;
- потере MQTT-соединения;
- восстановлении MQTT-соединения;
- ошибке GPS;
- ошибке CAN;
- ошибке чтения ADC;
- ошибке выполнения команды;
- срабатывании watchdog.

## 7. Функциональные требования

### 7.1. Инициализация

При старте устройство должно:

1. загрузить конфигурацию;
2. инициализировать GPIO;
3. инициализировать GPS;
4. инициализировать CAN/TWAI, если включено;
5. подключиться к сети;
6. подключиться к MQTT broker;
7. подписаться на topic команд;
8. отправить `heartbeat` со статусом `Online`;
9. начать периодическую отправку телеметрии.

### 7.2. Телеметрия

Прошивка должна:

- отправлять телеметрию с настраиваемым интервалом;
- поддерживать интервал по умолчанию 5000 мс;
- ограничивать минимальный интервал, например 1000 мс;
- не блокировать основной цикл при ожидании GPS или сети;
- передавать последнее известное значение, если новый GPS fix временно недоступен;
- помечать устаревшие координаты флагом или возрастом данных.

### 7.3. Команды

Прошивка должна:

- принимать команды только из разрешенного MQTT topic;
- проверять `deviceId` и `carId`;
- проверять `expiresAt`;
- игнорировать повторно полученные `commandId`;
- отправлять результат по каждой принятой команде;
- выполнять команды управления GPIO через отдельный слой драйверов;
- иметь защиту от слишком длинного payload и неизвестных `commandType`.

### 7.4. Состояния устройства

Минимальные состояния:

| Состояние | Описание |
| --- | --- |
| `Booting` | Идет старт прошивки |
| `ConnectingNetwork` | Подключение к сети |
| `ConnectingMqtt` | Подключение к MQTT |
| `Online` | Устройство работает штатно |
| `OfflineBuffering` | Нет связи, данные буферизуются |
| `Maintenance` | Сервисный режим |
| `Fault` | Есть критическая ошибка |

### 7.5. Работа без сети

При потере сети устройство должно:

- продолжать читать датчики;
- пытаться переподключиться с backoff;
- не зависать в блокирующих циклах;
- буферизовать ограниченное число последних telemetry-сообщений, если включен offline buffer;
- после восстановления связи отправить heartbeat и диагностическое событие;
- не выполнять устаревшие команды.

Для MVP допускается не сохранять буфер после перезагрузки. Для production версии требуется NVS или внешнее хранилище с ограничением размера.

### 7.6. Безопасность GPIO

Прошивка должна:

- приводить управляющие GPIO в безопасное состояние при старте;
- ограничивать длительность импульса реле;
- не держать реле открытия/закрытия постоянно включенными;
- логировать результат команды;
- не включать одновременно взаимоисключающие реле;
- иметь программную защиту от дребезга команд.

## 8. Нефункциональные требования

### 8.1. Надежность

- Основной цикл не должен блокироваться длительными `delay`.
- Должен использоваться watchdog.
- Устройство должно автоматически восстанавливать Wi-Fi и MQTT-соединение.
- Перезагрузка не должна приводить к случайному открытию дверей или изменению блокировки двигателя.
- Ошибки отдельных модулей не должны останавливать всю прошивку, если устройство может продолжать работу.

### 8.2. Производительность

- Размер JSON должен быть контролируемым и не превышать лимиты MQTT broker.
- Парсинг команд должен быть ограничен по размеру payload.
- Частота телеметрии должна настраиваться без перепрошивки.
- Цикл обработки должен сохранять отзывчивость к командам.

### 8.3. Безопасность

MVP:

- не хранить пароли в git;
- вынести секреты в локальный `config.h`;
- проверять идентификаторы устройства в командах;
- не исполнять просроченные команды.

Production:

- MQTT over TLS;
- уникальные credentials на каждое устройство;
- ротация credentials;
- подпись или HMAC для команд;
- защищенный OTA;
- запрет debug-команд в production-сборке;
- audit trail на backend.

### 8.4. Наблюдаемость

Прошивка должна предоставлять:

- heartbeat;
- diagnostics topic;
- firmware version;
- uptime;
- reset reason, если доступно;
- free heap;
- статус сети;
- статус MQTT;
- статус GPS;
- статус CAN.

## 9. Конфигурация

Конфигурация должна включать:

- `DEVICE_ID`;
- `CAR_ID`;
- Wi-Fi SSID и пароль для MVP;
- MQTT host, port, username, password;
- флаг TLS;
- интервалы telemetry и heartbeat;
- GPIO mapping;
- флаги включения GPS, CAN, OTA, offline buffer;
- лимиты payload и буфера;
- версию схемы сообщений.

Секреты и локальные параметры не должны попадать в git.

Рекомендуемые файлы:

```text
include/config.example.h
include/config.h
```

`config.example.h` хранится в git, `config.h` игнорируется.

## 10. Взаимодействие с микросервисами

### 10.1. События, которые должен выпускать backend после приема данных

`Telematics/IoT Service` может публиковать:

- `TelemetryReceived`;
- `DeviceHeartbeatReceived`;
- `DeviceDiagnosticReceived`;
- `VehicleCommandSucceeded`;
- `VehicleCommandFailed`;
- `VehicleLocationChanged`;
- `VehicleSpeedLimitExceeded`;
- `HarshAccelerationDetected`;
- `HarshBrakingDetected`;
- `VehicleIgnitionChanged`;
- `VehicleConnectivityLost`;
- `VehicleConnectivityRestored`.

ESP32 эти события не публикует напрямую. Оно публикует только MQTT-сообщения технического уровня.

### 10.2. Границы ответственности

| Зона | ESP32 | Backend |
| --- | --- | --- |
| Сбор GPS | Да | Нет |
| Сбор CAN | Да | Нет |
| Расчет стоимости поездки | Нет | Да |
| Проверка прав клиента | Нет | Да |
| Решение открыть автомобиль | Нет | Да |
| Исполнение команды открытия | Да | Нет |
| Хранение истории поездки | Нет | Да |
| Диагностика устройства | Да | Да |
| OTA-оркестрация | Частично | Да |

## 11. Архитектура прошивки

Рекомендуемая структура модулей:

```text
src/
  main.cpp
  AppController.cpp
  NetworkManager.cpp
  MqttClient.cpp
  TelemetryService.cpp
  CommandHandler.cpp
  GpsService.cpp
  CanService.cpp
  VehicleIo.cpp
  DiagnosticsService.cpp
  ConfigStore.cpp
include/
  AppConfig.h
  MessageContracts.h
  DeviceState.h
  VehicleState.h
  config.example.h
```

Назначение:

- `AppController` - жизненный цикл устройства;
- `NetworkManager` - Wi-Fi/GSM подключение;
- `MqttClient` - MQTT publish/subscribe;
- `TelemetryService` - сбор и отправка телеметрии;
- `CommandHandler` - валидация и выполнение команд;
- `GpsService` - чтение координат;
- `CanService` - чтение CAN/TWAI;
- `VehicleIo` - управление GPIO и реле;
- `DiagnosticsService` - диагностика и heartbeat;
- `ConfigStore` - локальная конфигурация и NVS.

## 12. Этапы разработки

### Этап 1. MVP на Wi-Fi и MQTT

Результат:

- подключение к Wi-Fi;
- подключение к MQTT broker;
- отправка heartbeat;
- отправка mock telemetry;
- прием команд;
- управление mock GPIO;
- command result;
- конфигурация через `config.h`.

Критерий готовности:

- на стенде видно heartbeat и telemetry в MQTT broker;
- команда `UnlockDoors` меняет состояние GPIO и возвращает `Succeeded`;
- неизвестная команда возвращает `Failed`.

### Этап 2. GPS и состояние устройства

Результат:

- чтение NEO-6M;
- отправка координат;
- обработка отсутствия GPS fix;
- состояние устройства;
- diagnostics topic.

Критерий готовности:

- координаты появляются в telemetry;
- при отключенном GPS отправляется диагностическая ошибка;
- устройство не зависает при отсутствии GPS.

### Этап 3. CAN/TWAI

Результат:

- подключение SN65HVD230;
- чтение тестовых CAN frames;
- mapping скорости, топлива, зажигания;
- конфигурируемое включение CAN.

Критерий готовности:

- тестовый CAN frame корректно отражается в telemetry;
- при отключенном CAN устройство продолжает работать.

### Этап 4. Устойчивость и безопасность

Результат:

- reconnect с backoff;
- watchdog;
- защита от дублей команд;
- проверка срока действия команд;
- ограничение размера payload;
- безопасные состояния GPIO.

Критерий готовности:

- после отключения и восстановления Wi-Fi устройство возвращается в `Online`;
- повторная команда с тем же `commandId` не исполняется второй раз;
- просроченная команда возвращает ошибку.

### Этап 5. Production hardening

Результат:

- MQTT over TLS;
- device credentials;
- OTA;
- NVS config;
- offline buffer;
- расширенная диагностика;
- профили сборки `dev`, `staging`, `production`.

Критерий готовности:

- устройство подключается к broker по TLS;
- OTA обновляет прошивку и сохраняет работоспособность после перезагрузки;
- production-сборка не содержит тестовых credentials.

## 13. Тестирование

### 13.1. Unit-тесты

Покрыть:

- парсинг команд;
- проверку `expiresAt`;
- проверку `deviceId` и `carId`;
- дедупликацию `commandId`;
- формирование JSON telemetry;
- формирование command result;
- состояние finite state machine.

### 13.2. Интеграционные тесты на стенде

Проверить:

- подключение к MQTT broker;
- публикацию telemetry;
- публикацию heartbeat;
- прием команд;
- управление GPIO;
- потерю и восстановление сети;
- отсутствие GPS;
- ошибку CAN.

### 13.3. Ручная приемка

Минимальный сценарий:

1. Залить прошивку на ESP32.
2. Открыть MQTT monitor.
3. Убедиться, что появился heartbeat.
4. Убедиться, что telemetry публикуется с заданным интервалом.
5. Отправить `GetState`.
6. Отправить `LockDoors`.
7. Отправить `UnlockDoors`.
8. Отправить неизвестную команду.
9. Отключить Wi-Fi и проверить reconnect.
10. Перезагрузить ESP32 и проверить безопасное состояние GPIO.

## 14. Критерии приемки MVP

MVP считается готовым, если:

- прошивка собирается без ошибок;
- настройки вынесены в локальный конфиг;
- устройство подключается к Wi-Fi и MQTT;
- устройство публикует heartbeat;
- устройство публикует telemetry;
- устройство принимает команды из `cars/{carId}/commands`;
- устройство отправляет результат команды;
- команды управления GPIO работают на стенде;
- просроченные и неизвестные команды не исполняются;
- при потере MQTT устройство пытается восстановить соединение;
- секреты не попадают в git;
- README содержит инструкцию по сборке, настройке и запуску.

## 15. Ограничения и открытые вопросы

Ограничения MVP:

- Wi-Fi вместо мобильной сети;
- JSON вместо бинарного протокола;
- mock или стендовые GPIO вместо реального автомобиля;
- упрощенный CAN mapping;
- без полноценного secure boot;
- без production OTA.

Открытые вопросы:

- какой MQTT broker будет использоваться в dev, staging и production;
- будет ли `carId` строковым UUID или числовым идентификатором;
- нужна ли отдельная регистрация устройства перед первым подключением;
- какой формат device credentials будет выбран;
- какие CAN ID нужны для конкретной модели автомобиля;
- какие команды допустимы в production;
- нужен ли резервный GSM/LTE канал в первой промышленной версии;
- какие SLA по частоте telemetry и допустимой задержке команд.

## 16. Definition of Done

Задача по прошивке считается выполненной, когда:

- код прошивки находится в репозитории;
- есть пример конфигурации без секретов;
- прошивка собирается локально;
- базовые сценарии проверены на ESP32;
- MQTT-контракты задокументированы;
- backend-разработчики могут реализовать `Telematics/IoT Service` по описанным topics и payload;
- известные ограничения описаны в README или отдельном документе;
- для production-рисков создан список последующих задач.
